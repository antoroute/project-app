## Synthèse

La base de code démontre les parcours principaux d'une messagerie chiffrée, mais elle ne satisfait pas encore les exigences de sécurité, fiabilité, portabilité et exploitation d'un produit publié. La priorité n'est pas l'ajout de fonctionnalités : elle est la fermeture des chemins de contournement d'autorisation, la sécurisation du cycle d'identité/appareil, la formalisation du protocole cryptographique et la création d'un environnement de livraison reproductible.

Les deux services TypeScript compilaient lors de l'audit. Flutter et Dart n'étaient pas présents dans l'environnement ; les builds Android, iOS, Windows et macOS n'ont pas été exécutés. Aucune suite de tests ni CI n'a été trouvée.

## Constatations hautes

- Les clés locales sont indexées par groupe/appareil et l'identifiant d'appareil est global, sans espace de noms de compte ; un changement de compte sur le même poste peut mélanger les identités cryptographiques.
- Le protocole V2 utilise des clés destinataires statiques. Il ne fournit pas, à lui seul, de forward secrecy contre une compromission ultérieure de ces clés ni de post-compromise security.
- La sérialisation signée/chiffrée n'est pas décrite par une spécification canonique indépendante ; certaines concaténations et conversions `codeUnits` rendent le format fragile entre plateformes.
- La file d'envoi persiste des objets via `Map.toString()`, sans format durable/versionné, idempotence ni machine d'état robuste.
- La configuration Flutter embarque `.env`; un secret partagé dans une application publique n'est pas un secret et ne peut pas authentifier « l'application officielle ».
- Android utilise encore un identifiant `com.example` et la signature debug en release. Les identifiants Apple sont ceux du template et les capacités de notifications ne sont pas préparées.
- `sqflite` et le scanner choisis ne couvrent pas Windows tels quels ; les notifications locales ne sont initialisées que pour Android/iOS. Les entitlements macOS release n'autorisent pas explicitement le réseau client.
- L'initialisation PostgreSQL repose sur un script de première création plutôt que sur des migrations versionnées. Un mot de passe par défaut apparaît dans le Compose d'infrastructure.
- Redis est configuré mais son rôle applicatif n'est pas démontré ; exposé ou non authentifié, il augmente la surface d'attaque sans bénéfice établi.
- Le Nginx versionné écoute en HTTP ; la topologie TLS réelle dépend de la VM et doit être inventoriée.

## Dépendances et qualité

Au jour de l'audit, `npm audit --omit=dev` signalait 12 vulnérabilités pour le service auth, dont 2 critiques, et 13 pour le service messaging, dont 1 critique. Ces chiffres sont temporels : la correction doit être accompagnée de tests, et un nouvel audit devra être exécuté au moment de la tâche.

Le dépôt ne définit pas de lint ou tests backend. Le client contient essentiellement la structure de test Flutter par défaut. Il n'existe pas de pipeline CI, de tests de contrat, de tests d'autorisation systématiques, de tests cryptographiques par vecteurs, de tests de migration/restauration ni de matrice de builds multiplateforme.

## Produit et publication

- Une application Google Play utilise déjà le nom « Trust Circle » pour un positionnement proche. Le nom, les marques et les domaines doivent être validés avant de réserver les identifiants définitifs.
- Les parcours de récupération et suppression de compte, blocage/signalement, support, politique de confidentialité et suppression Web restent à finaliser.
- Les fiches de confidentialité des stores doivent distinguer contenu E2EE et métadonnées détenues par le serveur.
- La distribution d'un produit cryptographique nécessite une vérification juridique et, selon les marchés visés, des déclarations ou qualifications appropriées. Ce document n'est pas un avis juridique.

## Architecture recommandée pour la V1

Conserver provisoirement les deux services Fastify afin de limiter la réécriture, mais mutualiser les contrats d'authentification et les contrôles d'autorisation dans des composants testés. Garder PostgreSQL comme source durable. Retirer Redis tant qu'il n'est pas nécessaire ; en cas de mise à l'échelle horizontale de Socket.IO, l'intégrer explicitement avec authentification et réseau privé.

Le client Web de messagerie est reporté : la gestion sécurisée de clés dans le navigateur, la persistance, la récupération et le multi-appareil exigeraient un chantier complet. La V1 Web est une landing page statique.

## Limites de l'audit

Il ne s'agit ni d'un pentest, ni d'un audit cryptographique indépendant, ni d'un avis juridique. Aucun accès à la VM, aux données réelles, aux journaux, au proxy externe, aux comptes stores ou aux certificats n'a été utilisé. Ces vérifications restent obligatoires avant publication.
